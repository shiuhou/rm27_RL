# M3C＋OS04A10 单目定位实验路线

版本：v1.0｜日期：2026-09-20｜性质：拟执行实验协议，不是已完成的测试报告。

## 0. 核心决策与证据边界

主线：**目标板成像 → 相机标定与数据集 → 电脑算法基线 → 同算法板端回放 → 板端实时处理 → 米制定位 → 飞控接口 → 低风险飞行。**

MaixCAM Pro 仅作为可选的早期取图平台，不作为必须完成的一次完整 SLAM 移植。M3C 和匹配底板已经可以使用时，直接用目标硬件采集，减少更换相机模式和标定的工作。

本轮用户提供的商品图明确写“M3C 1G 64EMMC 核心板”，芯片可读丝印为“AX630”。据此按**标称 1 GB 内存、64 GB eMMC 的 M3C＋OS04A10**规划，而不是沿用前文 AX620A、四核 A7、2 GB 的 M3AXPI 配置。商品图片不是实际设备读出；“AX630”短丝印不足以独立核定完整芯片后缀、CPU 频率、底板和 SDK。官方 AX630C／MaixCAM2 的相关资料可作为核对入口，但不得在没有核对时把整机全部配置套到该 SKU。[S1–S3]

官方 MaixCAM2 资料列 AX630C、双核 A53 1.2 GHz、3.2 TOPS INT8、1/4 GB 内存版本，并提供核心板相关资料；这说明有对应平台生态，不证明图中具体核心板的软件环境、可用内存或板端 SLAM 帧率。MaixCAM Pro 是另一条 SG2002／256 MB 平台。[S1–S2]

本轮读取了图片、官方资料、stella_vslam 上游说明与项目硬件账本；未取得用户板端系统读出、镜头标定、相机录像或 IMU 数据。没有在 M3C、MaixCAM Pro、飞控上执行任何实验，也未编译 SLAM。`maixcam2_dart` 本轮读取失败，不宣称已审查其完整当前代码。没有修改用户仓库或飞控。

本包只附只读环境采集脚本和实验元数据模板。脚本做过 `sh -n` 语法检查，未在目标板运行；它不会验证相机或 SLAM 性能。

## 1. 三个不同的完成目标

1. **视觉可用**：真实 OS04A10 图像经过正确标定后，可以初始化、连续跟踪、构建/复用地图。
2. **板端可用**：不依赖电脑处理，M3C 能在限定内存、功耗和延迟下持续运行；慢帧和失效被识别，而不是无限排队。
3. **控制可用**：输出尺度、重力方向、坐标变换、时间、质量和重置语义正确的状态，经过飞控和安全验证。

第一项成功不证明第二项；第二项成功不证明第三项。纯单目几何地图的任意尺度不能直接作为米制 ExternalNav 输入。外部计算和外部参考测量可以用于实验，不因此成为最终自主架构的一部分。

## 2. 算法分工

| 算法 | 本轮角色 | 采用条件 |
|---|---|---|
| stella_vslam 的 ORB 几何路线 | 第一条纯单目基线；板端完整建图与已有地图定位的比较 | 先在电脑构建成功并锁定提交，再移植目标架构 |
| ORB-SLAM3 | 有需要时的几何对照；也可评估其单目惯性模式 | 不要求第一轮同时编译所有方法；排除输入问题后再加入 |
| OpenVINS 单目＋IMU | 首选视觉惯性里程计候选，为机载状态估计服务 | 有可靠原始 IMU、时间与外参后才启动；不是给 stella 增加一个参数 |
| MASt3R-SLAM | 可选电脑端学习方法对照，检查学习型三维先验能否改善难序列 | 有合适 GPU 时进行；不作为 M3C 上原样部署的承诺 |

stella 官方支持地图保存/加载及 localization-only。OpenVINS 支持 ROS-free 构建，但官方说明这种集成支持有限，需要自己正确送入图像、IMU 与配置。MASt3R-SLAM 是稠密单目方法，作者实现使用 CUDA；电脑结果不能直接换算成小板性能。[S4–S8]

**不把“看起来最新”当作选择依据。**选定阶段的评价问题后，固定同一数据、输入几何、测量参考和计时范围，再比较算法。

## 3. 阶段总览

本文编号用 VSL，避免与项目已有 M0–M4、G0–G5 混淆。

| 阶段 | 环境 | 具体交付 | 进入下一阶段的条件 |
|---|---|---|---|
| VSL-0 | M3C＋匹配底板 | 硬件/镜像/SDK/资源快照 | 能辨认实际架构，能复原工作环境，接口不靠猜 |
| VSL-1 | 目标相机；Pro 可选 | 连续图像、帧元数据、取图性能报告 | 图像无破损、读帧连续，时间来源明确 |
| VSL-2 | 相机＋电脑 | 标定包、固定场景数据、独立验证序列 | 模型匹配最终输入，标定误差与边缘残差可接受 |
| VSL-3 | 电脑 | 官方序列与自采序列的单目轨迹、状态和误差 | 基线安装成立，自采慢速数据可以重复跟踪 |
| VSL-4 | M3C 离线 | 同数据板端运行、构建记录与资源剖析 | 程序稳定、内存可控，知道性能瓶颈在哪里 |
| VSL-5 | M3C 实时 | 直接取帧、实时估计、健康状态与长时测试 | 无持续积压，满足本协议的低速开发性能门槛 |
| VSL-6 | 相机＋可选 IMU | 米制 VIO 或带米制坐标约束的地图定位 | 尺度/坐标/时间/失效已通过独立参考验证 |
| VSL-7 | ArduPilot SITL＋拆桨真飞控 | ExternalNav 适配器和故障注入报告 | 方向、重置、过期、失联与接管行为正确 |
| VSL-8 | 受保护真机场地 | 影子记录、低速闭环、任务运动适用范围 | 独立基础飞行合格，再逐级验收视觉辅助能力 |

VSL-3 的公共数据集安装检查可以与 VSL-0/1 并行。VSL-6 的 IMU 采集和标定也可在板端性能测试时并行；不必等待完整大地图 SLAM 在板上达标才研究有界状态的 VIO。

## 5. VSL-0：冻结真实平台，不再按产品简称推断

### 实现目标

取得可以追溯的硬件/软件账本，并证明系统能够稳定启动和恢复。区分四种不同量：物理 RAM、Linux 可见 RAM、启动后空闲 RAM、eMMC 存储。

### 操作

将本包 `collect_m3c_env.sh` 复制到目标板，在该板终端执行：

```sh
sh collect_m3c_env.sh ./m3c_env_01
```

查看 `environment.txt` 并填写 `MANUAL_NOTES.md`。核对设备树、CPU 架构、镜像来源、SDK 与供应方该 SKU 的资料；泛化的设备树名称不能单独证明芯片后缀。记录当前相机启动命令，而不是先更新到最新分支。

镜像和现有项目代码各自保留可回退快照；有 Git 的工作区记录 commit、工作区差异与子模块提交。若系统无 Git，则至少保存程序/配置校验值和镜像版本。

不直接运行前文给 AX620A 的旧相机脚本，不默认用 `arm-linux-gnueabihf`。核实用户空间架构后才选工具链。

### 验收

能启动、取得信息、找到匹配相机驱动入口；已记录底板与模组连接。未知芯片后缀/电气接口必须在烧录或接线前关闭；算法公共数据测试不受此阻塞。

交付：`hardware_baseline.md`、`environment.txt`、`versions.lock`、启动命令与配置副本。

## 6. VSL-1：建立可记录、可解释的图像链路

### 实现目标

不用 SLAM，先稳定取得正确的图像及必要元数据。接口可用 MaixPy/MaixCDK 的现有相机层，最终采用哪条路径以目标镜像为准。官方 MaixPy 的相机文档提供图像读取、灰度、曝光、帧率等接口，同时说明输出比例可能引入裁剪、高帧率模式可能有偏移。[S3]

### 起始设置（实验建议）

首选先用约 640 像素宽、30 FPS、单曝光模式；640×360 是候选输出，不保证所有 SDK 原样支持。采用其他输出时，保存真实裁剪/缩放关系并对该输入标定。不要一开始追求 180/360 FPS。

先使用普通直视镜头，不同时引入自制全景镜。先在明亮环境中确认多个任务距离上的清晰度，例如 0.5、1、2、4 m；这些是实验距离，不是镜头规格。禁止用肉眼调整的 `lens_corr(strength=...)` 代替几何标定。

测试可控曝光 1、2、4 ms，光照不足时允许先用更长曝光建立静态图像基线，随后单独评估运动模糊。关闭或固定会改变几何/时序的电子防抖、动态裁剪；HDR、强时域降噪等处理能控制时分别记录状态。不能为了暗处明亮而无记录地让曝光无限拉长。

### 最小采集内容

```text
frame_id / driver_seq（有则保留）
原始 SDK 时间戳及单位、时钟域、含义
应用收到帧的 monotonic 时间
曝光、增益、输出模式、宽高、像素格式、stride
图像文件路径；采集/存储异常
```

无法取得曝光时刻时，保留 `timestamp_source=host_receive` 或 `unknown`，不要改名成曝光时间。没有驱动序号时，只能报告应用读帧率，不能声称传感器丢帧率已经测定。

建议第一批数据保存图像序列与 sidecar CSV；同时保留短段高质量彩色视频给学习方法对照。PNG 等编码/写盘也可能造成阻塞，采集与写盘用有界缓冲并记录丢帧，不允许用无限队列掩盖速度不足。最终实时性能测试还需分别测开/关录像的影响。

### 验收建议

连续采集 10 min，无花屏、尺寸变化或意外重启；时间戳不倒退，帧编号可追溯。目标 30 FPS 时先以应用平均读帧≥28 FPS、已具备统计条件下非预期丢帧<1%为开发门槛。记录全部长间隔，不用平均值代替尾部行为。

交付：`capture_test.csv`、一段可播放视频、样本图、`camera_pipeline.md`。

## 7. VSL-2：标定并建立能重复比较的数据集

### 实现目标

让算法知道最终输入像素的成像几何，并把“测试动作”变成固定协议。

### 标定

使用棋盘格（例如 9×6 内角点，而非方格数）或 Aprilgrid，固定镜头与对焦，采集约 30–50 个有效视角，覆盖中心、边缘、不同距离和倾角。普通镜头首先尝试匹配畸变的针孔模型；鱼眼用对应模型。依据残差判断，不依据产品名字判断。OpenCV 与 OpenVINS/Kalibr 官方均给出了内参/畸变标定流程。[S9–S10]

约 20% 独立图像不参与内参拟合，用于验证；更换镜头、对焦、输出模式、裁剪或防抖状态后复核标定。不要给已经去畸变的图像再套一次旧畸变参数。

保存 `fx,fy,cx,cy`、畸变参数、成像模型、宽高、模式、拟合与验证残差。第一轮建议拟合 RMS<0.5 px、独立验证 RMS<1 px，另检查边缘是否系统性偏移。这是开发目标，不是所有镜头的通用验收线。

### 录制协议

每类先录 3 次，分调参与留出验证；建图与重定位必须使用不同录制轮次。

| 数据 ID | 运动/场景 | 判断重点 |
|---|---|---|
| D00 | 先平移完成初始化，再静止 60 s | 静止抖动、漂移、误报；纯单目未初始化时静止不出位姿不是故障 |
| D01 | 沿量尺/导轨做约 1–2 m 平移和返回 | 方向、相对几何与距离复现；测量精度和夹具误差要记录 |
| D02 | 约 2×2 m 小闭环，含近远景 | 连续跟踪、回环；关闭回环/启用回环分别报告 |
| D03 | 平移叠加逐渐加快的 yaw/pitch；另加初始化后的纯旋转 | 运动模糊、滚动快门、可接受角速度范围 |
| D04 | 缓慢靠近再远离有纹理的目标平面 | 前向运动、近距离失焦、视野占满时的局限 |
| D05 | 同路径、两档光照、固定与自动曝光分别录 | 成像处理和环境变化的影响 |
| D06 | 遮挡约0.2/0.5/1 s后解除 | 失效标记、重定位、是否重置或坐标跳变 |
| D07 | 机库视角/相似槽位、低纹理、动态人员等任务背景 | 起飞前定位、场景歧义与动态干扰；不以白墙测试否定所有场景 |

仅沿地面画一条线不等于拥有全程六自由度真值。量尺/导轨可以验证受限运动；严格 ATE 需要同步的独立轨迹参考。用标记辅助提供尺度/定位的实验，与无标记实验分开标记，不隐瞒信息来源。

交付：标定原图、`camera.yaml`、标定报告、`dataset_manifest.yaml`、全部录制原始数据与校验值。

## 8. VSL-3：电脑上的单目基线与可选前沿对照

### 实现目标

先隔离软件安装问题，再确认真实图像是否适合该方法。

在独立电脑工作区/容器构建 stella_vslam，固定算法、示例、依赖和词典版本。先用 EuRoC 等官方例程支持的数据集只输入单相机图像，禁用 IMU/第二相机以保证纯单目条件。EuRoC 自带双目与 IMU 并不意味着必须全部输入；OpenVINS 官方教程也明确区分输入配置。[S4,S11]

然后以自采标定运行 D00–D07。视频例程可快速排错，但其以配置 FPS 推进时间的实现不能代替真实每帧时间；正式回放器应读取图像＋时间 CSV。需要保存实时输出的轨迹和每帧状态，不只保存结束后优化过的轨迹。

### 必须输出

初始化成功与耗时；初始化后有效跟踪时间比例；最长中断；重定位/重置次数；每帧跟踪、前处理与总耗时；地图/关键帧数量；轨迹与失败原因。

区分 `pose_online` 与 `pose_optimized`。回环修正后起终点接近不是独立精度证明，更不能把回环前的漂移删除。

有 GPU 时，加 MASt3R-SLAM 作为离线/电脑对照。它的稠密重建能力与小板持续状态估计是不同目标；使用同一原始录制并记录各自预处理差异。GPU 方法改善某段视频，只能支持该条件下的表现，不直接给出板端可迁移性。[S8]

### 评价规则

纯单目用一次全局 Sim(3) 对齐评价“允许尺度对齐后的轨迹形状”；米制 VIO/米制地图定位用不允许缩放的 SE(3) 或事先明确的重力/航向对齐。不能给每个小段重新缩放来掩盖尺度漂移。没有参考轨迹时，不计算虚假的 ATE。

第一轮慢速正常场景要求3/3次初始化、有效跟踪覆盖率≥95%作为开发推进条件；难场景可以失败，但须给出发生条件和可检测性，不要求这一阶段已经抵抗所有遮挡。

交付：`pc_baseline_report.md`、轨迹、每帧状态、计时、环境版本与留出结果。

## 9. VSL-4：同一算法、同一数据，迁移到 M3C 离线运行

### 实现目标

排除相机和网络波动，仅测目标 CPU/内存与移植代价。

使用 VSL-0 核定的工具链，构建无显示依赖的运行器。先保持与 PC 相同输入和参数；若要调整，作为新实验条件保存。词典、地图、库的 ABI/序列化版本也要保持匹配。构建内存不足可在 PC 交叉编译，不把“板上编译OOM”误当“算法运行必然OOM”。

移植范围限定为构建与输入适配，不重写 SLAM。复用已有相机程序前应在实际工作区检查它；本包不提供猜测的 AX630 SDK 函数签名。不要把上层画面关闭等同于已经移除编译时的所有 viewer 依赖。

### 记录与优化顺序

记录启动峰值、运行峰值 RSS、系统 MemAvailable、各线程 CPU、温度、频率、完整回放耗时和地图增长。首先在小数据段验证，再运行长数据。

优化按可归因顺序：取消无关 GUI/检测/编码 → 控制图像复制/颜色转换 → 量化不同分辨率的速度与跟踪损失 → 调整特征/关键帧/局部窗口 → 再考虑学习前端或硬件加速。任何“加速”必须附跟踪覆盖率和误差结果。

只在 CPU 瓶颈已确认时考虑更强 CPU；NPU TOPS 不直接代表特征匹配、图优化和地图维护的计算能力。

### 验收

能在板上完成同一数据的回放且不崩溃，输出无明显平台特有异常；长段内存不无限增长。慢于实时也可以完成本阶段，但必须报告速率，不能提前宣布“机载实时SLAM完成”。

交付：`build_record.md`、目标二进制/依赖清单、`board_replay_profile.csv`、PC/板端差异报告。

## 10. VSL-5：直接取图实时运行，并比较完整SLAM与已有地图定位

### 实现目标

不经本机 H.264→RTSP→解码绕行，直接把 SDK 输出图像送入运行器，并定义可靠的失效状态。

建议接口：

```text
capture_adapter
→ Frame(image, sequence, measurement_time, arrival_time, clock_id, calibration_id)
→ preprocess / tracker / map or localizer
→ PoseEstimate(measurement_time, publication_time, pose, state, map_id, reset_counter)
```

处理 SDK 图像时必须核对 stride、像素格式、内存所有权和释放时机；异步处理不能在 SDK 已回收的缓冲区上继续读。取 NV12/NV21 亮度平面可减少转换，但应先核对实际格式，不凭名称猜内存布局。

实时队列先采用“最多保留一张等待处理的最新帧”，允许显式跳帧并记录；不能无限排队。估计状态至少区分 INITIALIZING / TRACKING / LOST / RELOCALIZING；它们是建议接口状态，不宣称各算法原生同名。

### A/B 两个运行模式

A：板上持续跟踪＋建图＋回环。

B：电脑使用该相机建好地图，板上加载后 localization-only，必要时比较受限局部里程计。地图必须来自可对应的静态场景和兼容相机/算法配置。stella 官方提供这些入口，但是否节省到满足 M3C 资源限制，要实测。[S4,S5]

B若达标、A不达标，结论是“已知地图定位可行，完整在线建图尚未达标”，不是“SLAM都不行”。

### 第一轮低速开发性能门槛（建议，非飞行安全认证）

| 项目 | 起始门槛 |
|---|---|
| 有效估计更新 | ≥15 Hz，后续再试30 Hz；重复发送旧姿态不计更新 |
| 主要跟踪耗时p95 | 15 Hz设置下≤66.7 ms；同时看p99和完整链路 |
| 曝光/有效观测时刻→输出年龄p95 | ≤100 ms；曝光时刻未核实则此项“未验证”，只能报告应用段延迟 |
| 持续性 | 连续10 min无崩溃、无限队列或持续内存上升 |
| 内存 | 保留至少约20%的Linux可见内存余量，且无持续swap换页；资源预算以实测为准 |
| 失效 | 过期/失跟显式标无效，不持续输出伪有效旧位置 |

延迟定义：`L = t_publish − t_measurement`，必须属于同一或已换算的时钟域。单独的 tracker 调用耗时不包含采集、排队、前处理与发送，不是 L。

迟滞造成的位置滞后量级可用 `e≈vL`理解：2 m/s与100 ms对应约0.2 m。因此本门槛适合起步验证，不证明高速近距离任务够用。

## 11. VSL-6：把任意尺度变成可用于控制的米制状态

### 路线 A：相机＋IMU，首选机载状态估计候选

采用 OpenVINS 单目＋IMU，或在条件明确后对照 ORB-SLAM3 单目惯性模式。先在 PC 用公共视觉惯性数据验证，再用本机数据；最后做目标板实时测试。不把 stella 的完成度转写为 VIO 已完成。

要获取的是原始角速度（rad/s）、加速度计比力（m/s²）及可靠采样时间，不是只有姿态角或接收时刻。优先使用与相机刚性连接、时间关系可控的 IMU。是否能够复用飞控 IMU，要单独核对原始数据链路与同步；普通姿态遥测不能替代完整惯性输入。

采集相机约30 Hz、IMU约200–500 Hz作为初始配置；实际稳定速率、抖动、缺样需要测量。进行相机内参、IMU噪声、相机—IMU外参与时间偏移标定。标定时需要足够的平移和转动激励；长时静态数据用于噪声分析，不能用短暂静置冒充完整噪声标定。[S9]

滚动快门的逐行读出不是单一相机—IMU时间偏移。短曝光减少模糊，不消除读出畸变。核查所选实现是否建模滚动快门；未建模时限定运动包线，若误差与角速度相关则单独调查读出模型/传感器，不靠增加IMU频率掩盖。

### 路线 B：固定场景的米制地图定位

场景固定且可建立测量约束时，可以给预建地图确定尺度、方向和原点，再在板上定位。保存“内部地图坐标→米制任务坐标”的变换及其标定版本；转换必须同时应用于对应的位置、速度、方向与不确定性，而非随手给某个输出乘常数。

单条已知长度只能提供有限尺度约束，不能自动确定完整三维方向；任务坐标和重力方向需由已知几何/测量另外确定。辅助标记使用和无标记实验分开；实验室允许放标记不意味着比赛可增加标记。

路线B不强制需要IMU，但只有当其启动、连续性、失跟、米制精度都通过时，才可作为控制输入候选。

### 独立验收

采用导轨/标记参考/动捕之一，并记录其不确定性。对独立录制的1–2 m位移先以误差≤5%作为开发目标；至少5次重新启动，检查尺度与坐标是否稳定。需要连续轨迹精度时增加同步轨迹真值。已给系统提供尺度的那段测量不能再冒充独立验证。

交付：`metric_localization_report.md`、标定包、独立参考、各次初始化结果、含尺度/重力/质量的输出契约。

## 12. VSL-7：接入 ArduPilot，但先不接管真机

项目硬件账本记录飞控路线为 ArduPilot。本阶段新增的是 ExternalNav 状态输入，不是把SLAM直接接到电机，也不是用目标装甲相对位姿冒充无人机全局位姿。已有 `TargetEstimate` 的目标感知职责保持独立。[S12]

### 接口契约

至少固定：观测/输出时刻与时钟域、位置单位、姿态变换方向、四元数顺序、世界/机体系、相机到机体外参、有效性、质量/不确定性、地图ID、重置计数。

定义 `T_AB` 为从B系到A系的变换，则若拿到 `T_WC`，机体状态为：

`T_WB = T_WC × inverse(T_BC)`。

算法可能返回 `T_CW`，不能跳过求逆核查；相机右/下/前与机体前/右/下不同。相机偏心补偿只能按约定做一次，不能适配器与飞控各做一次。

ArduPilot 官方首选 `ODOMETRY` 接收外部估计，并列出了米制位置、坐标、质量和重置字段。正式配置需对照实际固件与现有EKF源，不能直接覆盖全部参数。官方列出的最低输入频率不是本项目高速控制充分条件。[S13]

### 验证顺序

1. 适配层单元测试：已知变换、三轴平移、旋转与相机偏心，检查符号和单位。
2. SITL 中提供与虚拟机体运动一致的估计，注入时间延迟、丢帧、冻结、重置、错误尺度；真值仅用于评分，不混入声称视觉闭环的链路。
3. 拆桨真飞控，手持整套相机/飞控移动，验证位置方向、姿态、质量和时序。
4. 启用源之前对备份参数做最小变更，验证估计器确实消费数据、不是只收到MAVLink。

真实手持相机与虚拟飞机没有物理运动一致性时，只能验证消息/时间/方向，不能把它当完整飞行闭环证明。

### 回环与失效

回环可能让全局地图坐标跳变；局部控制所需连续状态与全局校正应分开处理。REP105 的 `odom`连续、`map`允许修正跳变，是可参考的组织方式，不要求使用ROS。[S14]

测试视觉遮挡、旧图重复、估计进程终止、连接中断和地图重置。分别验证拒绝过期数据、显式失效、重置处理与人工接管。位置估计失效时，零速度命令不保证悬停；不得默认故障下一律RTL/Loiter。具体中止与降落行为由已验证飞控能力和场地制定。

VIO与飞控若使用相关IMU/融合状态，要评估重复使用同源信息的问题；不要未经分析把飞控EKF状态反喂给VIO，再当独立观测返回EKF。

交付：接口文档、参数变更清单、原始日志、自动测试和故障响应报告。

## 13. VSL-8：影子模式、低速闭环，再建立任务适用范围

### 8A 影子模式（Shadow mode）

视觉板在真实飞机上运行和记录，但不参与控制。先做无动力装机确认，再在独立飞行基线合格的条件下飞行。记录增加的完整质量、供电压降、温度、振动、图像与飞控日志。

不把拆桨试验当成验证了带桨振动，也不把三自由度台架当成验证了自由平移定位。所有带桨试验均在防护场地、独立遥控接管与安全员条件下进行。

### 8B 限定低速闭环

从人工建立的稳定悬停状态开始，只验证外部状态参与后的保持，再做单轴短距离移动与制动。建议初始动作约0.2–0.3 m/s、0.5 m距离，再扩到1–2 m；不是安全速度保证，按场地、定位误差、刹停数据和机体余量调整。

先安排5次冻结配置下的完整试验，保留失败。相机失效、异常跳变、命令方向错误、持续振荡、电源重启、过热、低电量、保护罩损坏或人员进入试验区时中止。人工接管后程序不得强行切回自主模式。

### 8C 任务运动与并发验证

在不真实接触目标的前提下，覆盖：从机库视角开始、上升后视野变化、连续转弯、前向接近目标、转向返回、目标占满视野、相似机位区分、重定位。冻结真正需要的速度/角速度范围，而不是用桌面慢速结果外推。

先让无人机到目标前的安全停止区再返回。接触、撞后恢复与精准入库保留为不同验收项目：SLAM负责区域定位，不直接证明装甲法线、有效接触或停机位容差。

加入绿灯/装甲检测时，测量“定位单独运行”与“定位＋检测＋通信＋日志”两种负载。同一相机在低分辨率定位和高分辨率小目标识别之间可能需要分路/调度，加入后重测整个图像链路及内存，不套单任务FPS。

交付：飞行适用包线、实际估计/响应误差、失败记录、安全退出结果、共享算力预算与下一阶段准入结论。

## 14. 共用数据、指标与判定纪律

建议新实验使用独立工作区或现有仓库中的新增实验子目录；以下只是职责建议，不声称文件已经存在于用户仓库：

```text
m3c_vslam_lab/
  docs/                 # 协议、接口、报告
  configs/              # 平台、相机、算法，含版本与来源
  adapters/             # 取图、IMU、飞控薄适配
  tools/                # 回放、统计、评估
  data/                 # 原始数据，通常不进Git
  results/              # 运行日志、轨迹、资源数据
```

最重要的交付程序不是漂亮Viewer，而是：`capture`、`calibrate`、`replay`、`live_estimate`、`evaluate`、`autopilot_adapter`六项职责。它们可以复用已有模块，不要求新造框架。

每次运行至少关联：硬件/底板/镜头、镜像和SDK、算法commit、参数、模式、标定、输入数据校验值、测试动作/光照、预定门槛和全部结果。

固定指标：初始化率；有效跟踪覆盖率；最长失效；重定位时间/重置数；在线与优化后轨迹；尺度误差；有参考时的ATE/RPE；采集/跟踪/端到端p50/p95/p99；峰值RSS/剩余内存/温度/功率；地图规模；并发业务影响。

对照实验只改变被研究的变量。标定、调参、建图、验证集分开；不同算法所需输入额外信息要公开。不能丢掉初始化失败、删掉遮挡片段、每段重新缩放、只统计恢复后轨迹，或者测试后放宽标准以得到PASS。

缺少某项测量时标 `not_measured`，不是填0；不确定性未知时不发全零协方差冒充绝对准确。单次或5次成功只允许推进开发，不构成比赛可靠性证明。

## 15. 失败之后的决策分支

| 现象 | 优先调查 | 不应直接下的结论 |
|---|---|---|
| 公共数据也无法运行 | 构建、配置、词典和例程版本 | OS04A10不适合SLAM |
| 公共数据正常，自采数据PC端失败 | 标定、清晰度、纹理、视差、滚动快门、时间 | 小板算力不够 |
| PC稳定，目标板编译失败 | ABI、工具链、依赖、指令集 | 算法运行性能不够 |
| 板端离线稳定，实时失败 | 取图格式/缓冲生命周期、排队、存储、线程调度 | 核心SLAM算法必然错误 |
| 跟踪快但内存持续增长 | 地图/关键帧管理和负载范围 | 仅降低分辨率就解决全部问题 |
| 完整建图不够，已有地图定位够 | 限定地图方案的适用条件，或比较有界VIO | 所有单目定位都不可用 |
| 加快转动后PC也失败 | 曝光、读出时序、相机模型/运动范围 | 买更大NPU一定解决 |
| 米制误差大、漂移大 | IMU时序/标定/激励、地图尺度、参考精度 | 仅换另一热门算法即可 |
| 桌面通过、带桨失败 | 振动、供电、相机安装、温度、IMU截断与场景变化 | 数据集成绩代表真机能力 |

只有经过剖析证实CPU/内存限制，而且受限地图/输入优化达不到目标时，才有证据决定换计算平台。OS04A10被验证的成像问题则对应镜头、曝光、滚动快门模型或传感器方向的改动；二者不能混为一谈。

## 16. 第一轮最有价值的里程碑

**用目标 M3C＋OS04A10 在固定模式采集一组经过标定的真实序列，电脑得到可复现的单目跟踪，然后同一序列在板上运行并给出CPU、内存和耗时报告。**

先交付 VSL-0～4 的证据，再确定实时架构。M3C尚无工作载板时，Pro可以先完成采集/标定/PC方法学习，但之后仍需以目标相机链路重做这些资格检查。这个阶段不要求飞行，不要求双目，不要求RL，也不要求GPU方法能直接迁移。
